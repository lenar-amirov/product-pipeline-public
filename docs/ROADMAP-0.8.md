# Roadmap 0.8 → 1.0: от чеклиста к системе с обратной связью

> Design-doc, 2026-07-03. Основан на трёх исследованиях: критика методологии,
> gap-анализ реальной (приватной) инициативы автора (июнь–июль 2026),
> конкурентный анализ AI-инструментов для PM (2025–2026).
> Рабочий язык документа — русский; при финализации релизов ключевые части
> переносятся в README/CHANGELOG на английском.

## Принцип редизайна

**Хребет инструмента — реестр гипотез и доказательств, а не номера шагов.**

Gap-анализ живой инициативы показал: реальная работа PM вращается вокруг
гипотез (одна опровергнута REAL-данными → стратегический разворот; несколько
подтверждены → переприоритизация), а «шаг N in_progress» — фон. Самая ценная
работа (ingestion внешнего дека, доработка ТЗ в Jira, sizing эксперимента) не
имела дома в пайплайне. Половина артефактов шагов остаётся заглушками, которые
ничто дальше не потребляет.

Рыночная рамка: две незанятые ниши — «состояние между сессиями» (ChatPRD
забывает контекст, официальный Anthropic PM-плагин stateless) и «честность
доказательств» (главная жалоба на Notion AI/ChatPRD — «уверенно неправильный
вывод утекает в roadmap»). Обе ниши — наши механики, но сегодня они
декоративные (проза в markdown). План превращает их в работающие.

**Шаг = способ добыть недостающее доказательство. Фаза закрыта, когда
доказательства собраны, а не когда шаги «пройдены».**

## 0.8 «Фундамент честности»

### E1. Реестр гипотез — машиночитаемое состояние (L)

Сейчас: гипотезы живут прозой в `hypotheses.md` / `validated-hypotheses.md`;
статусы, confidence и связи с источниками не парсятся.

Делаем: `output/hypotheses.yaml` — единственный источник истины о гипотезах.
Markdown-файлы становятся генерируемыми представлениями (view), не источником.

```yaml
# output/hypotheses.yaml (пример вымышленный)
- id: H4
  title: "Пользователи бросают чекаут из-за недоверия к оплате"
  track: B                       # A | B | cross
  status: confirmed              # draft | testing | confirmed | refuted | parked
  evidence_type: REAL            # REAL | SYNTHETIC | INFERRED | AMBIGUOUS
  confidence: 0.7                # валидируется против диапазона типа
  sources:
    - file: research/analytics-data.md
      ref: "дашборд оплат, стр. 3: онлайн-оплата подключена в N% заказов"
      type: REAL
      date: 2026-06-10
  history:
    - date: 2026-06-10
      change: "INFERRED 0.4 → REAL 0.7 (внутренняя аналитика)"
  solutions: [S2]                # связь с solution-гипотезами
```

Критерии приёмки:
- `hypotheses.md` / `validated-hypotheses.md` генерируются из YAML командой
  (или на SessionStart), ручная правка YAML — допустимый вход.
- Каждая гипотеза без `sources` не может иметь `evidence_type: REAL`.
- История переходов (SYNTHETIC → REAL) пишется автоматически.
- Миграция: скрипт конвертирует существующие md-реестры в YAML
  (dogfood-проверка на реальной инициативе автора).

### E2. Evidence ledger и валидаторы (M)

Сейчас: `evidence-typing.md` — правило-текст. В живой инициативе встретились
confidence вне диапазона своего типа и противоречие двух источников по одной
метрике, неделями державшее вес топ-гипотезы.

Делаем: `tools/scripts/validate-evidence.py`, запускается на SessionStart и
перед гейтами:
- confidence в диапазоне своего типа (REAL 0.6–1.0 и т.д.) — иначе warning
  в вывод хука;
- у REAL-гипотезы есть ≥1 источник с файлом и датой;
- флаг `data_inconsistency`: если два источника дают расходящиеся значения
  одной метрики (>10%), гипотеза получает ⚠️ и не может держать
  confidence >0.6 до сверки;
- отчёт «доказательная сводка»: N гипотез confirmed REAL / testing / refuted.

Критерии приёмки: прогон на реальной инициативе автора находит оба известных
дефекта (confidence вне диапазона; несверённая метрика) без ложных
срабатываний.

### E3. Digest и статус — производные от реестра (M)

Сейчас: `scan-initiatives.py` парсит CONTEXT.md регексами; digest не знает
о вердиктах гипотез; «4/20» считается по шагам.

Делаем:
- digest собирает из `hypotheses.yaml`: «подтверждено REAL: H2, H4;
  опровергнуто: H1; открыто: H5/H6» — это полезнее для детекции
  пересечений, чем обрезанные поля CONTEXT.md;
- прогресс инициативы = доказательная готовность фаз (см. E9), пока фаз нет —
  оставить шаги, но считать от включённых в pipeline_config (фикс «4/18 vs
  4/20»);
- единый `tools/scripts/pipeline_constants.py`: PIPELINE_STEPS, лейблы, фазы —
  импортируется всеми (status.py, scan-initiatives.py, app.py,
  static_export.py). Убирает 4 разъехавшиеся копии.

### E4. Технический долг из аудита 0.7.x (M)

Пакетом, без изменения сути:
- frontmatter для `setup-initiative` и `user-test-concept` (сейчас скиллы не
  триггерятся по смыслу);
- фикс `generate-pptx.py` (ищет инициативы не в том корне — не работает
  вообще);
- веб-дашборд: `debug=False`, bind на 127.0.0.1, экранирование markdown
  (XSS), `resolve().is_relative_to()` против path traversal, whitelist
  расширений загрузки CJM;
- README: задокументировать scan-initiatives/digest, веб-дашборд,
  static_export; версию 0.7.x → актуальной; таблица «PM Copilot vs
  официальный Anthropic PM-плагин» (позиционирование: плагин + состояние +
  честность против stateless-команд).

## 0.9 «Петли»

### E5. Внешние зависимости с SLA вместо вечных pending (M)

Сейчас: `pending.*` — строки без владельца и срока. В живой инициативе
бриф-опрос неделями висел «готов к отправке», а задача аналитику ушла в
двухнедельную просрочку — инструмент молчал.

Делаем: `pending` → `dependencies` в status.json (пример вымышленный):

```json
{
  "id": "analytics_funnel_split",
  "kind": "analytics",
  "owner": "аналитик команды",
  "jira": "ANLT-123",
  "created": "2026-06-10",
  "deadline": "2026-06-17",
  "blocks": ["H5", "H6", "sizing:experiment-A"]
}
```

SessionStart показывает возраст и просрочку; при просрочке инструмент обязан
предложить выбор: пнуть владельца / перенести срок / перейти на синтетику
(с автоматическим даунгрейдом confidence зависимых гипотез) / осознанно
скипнуть (status `skipped`, не вечный pending). Выбор фиксируется в
decisions.md.

### E6. Двусторонний Jira-цикл (M)

Сейчас: MCP умеет создавать/править задачи, но статусы не возвращаются;
доработка ТЗ в Jira не отражается в инициативе.

Делаем:
- на SessionStart (если MCP доступен) — опрос статусов задач из
  `dependencies[].jira`: закрыта → предложить активировать приём результатов;
  изменено описание → отметить в decisions.md;
- `/create-tickets` и брифы шага 4 создают задачи сразу с обратной ссылкой
  (label `initiative:<slug>`), id пишется в dependencies.

Rovo заперт в Atlassian; мы живём в файлах и соединяем Jira с чем угодно —
это конкурентное преимущество, его надо дожать.

### E7. `/ingest` — первоклассный приём внешних данных (L)

Сейчас: переворот живой инициативы случился через ad-hoc хак (ручной рендер
многостраничного PDF-дека во внешнем скрипте). В пайплайне нет пути для «мне
принесли дек/выгрузку/страницу».

Делаем: команда `/ingest <файл|Confluence pageID|URL>`:
1. парсинг (PDF → текст+числа, xlsx/csv, Confluence через MCP);
2. извлечение ключевых метрик и находок с привязкой к месту
   («слайд 12: CTR по surface X ≫ Y»);
3. **мэппинг на открытые гипотезы**: «найдено REAL для H2», «противоречит
   H1» — с предложением обновить реестр (E1) и апгрейднуть/опровергнуть;
4. типизация по источнику (внутренняя аналитика = REAL; чужой бенчмарк =
   INFERRED) и запись в sources;
5. остаток (не смэппленное) — в `research/inbox-notes.md` как сырьё.

Критерий приёмки: прогон на реальном внутреннем деке из инициативы автора
воспроизводит вручную сделанный июньский результат (закрытие вопросов брифа,
опровержение одной из гипотез) за один вызов.

### E8. Anti-generic self-check документов (S)

Каждый генерируемый артефакт (презентация, PRD, брифы) проходит самопроверку:
- нет утверждений без источника (`[source: ...]`);
- нет плейсхолдер-советов («ensure compliance», «improve UX»);
- proof-слайды: только REAL (SYNTHETIC → speaker notes) — механически, а не
  по памяти модели.

Это прямой удар в задокументированную боль конкурентов («30% вывода Notion AI
generic или галлюцинации») — вынести в README как гарантию.

## 1.0 «Фазы и гейты»

### E9. Фазовая модель вместо нумерации 0–19 (L)

Сейчас: линейный список с костылями (5.5, 6a/6b, 8.5); шаги-церемонии (9, 11,
18, 19) выглядят обязательными; «done по шагам» ≠ «доказано».

Делаем: 7 фаз с exit-критериями; прежние шаги — инструменты внутри фаз:

| Фаза | Инструменты (быв. шаги) | Exit-критерий |
|---|---|---|
| Frame | 0, 1 | metric+baseline+target+kill criteria заполнены |
| Evidence | 2, 3, 4, 5, /ingest | ≥2 гипотезы confirmed REAL ≥0.6, без data_inconsistency |
| Solution | 7, 8, 8.5, 9 | решения проскорены (ICE/SIF), связаны с гипотезами |
| Bet (Gate 1) | 10 | гейт пройден (E10) |
| Build | 11, 12, 13, /create-tickets | PRD approved, оценка дев-команды есть |
| Launch | 14, 15 (Gate 2), 16, 17, 18 | эксперимент решён: ship/kill/iterate |
| Learn | новое (E12) | метрика сверена с target; факты в knowledge base |

- Дизайн/суппорт-воркфлоу (9, 11, 19) — опциональные подключаемые модули, не
  ступени основного трека.
- status.json v2: `phases` с состоянием + обратная совместимость (миграция
  скриптом). Прогресс — «Evidence: 3/4 критериев», не «4/20».
- Переходы разрешены доказательствами, а не порядком: если /ingest закрыл
  вопросы фазы Evidence — Solution открывается, даже если опрос ещё в поле.

### E10. Гейты как рубиконы + challenge-режим (M)

Сейчас: Gate 1/2 — флажок `pending.gate1_challenge`.

Делаем:
- **preconditions** (машинные): Gate 1 требует ≥2 confirmed REAL, 0
  data_inconsistency, target зафиксирован; иначе сборка презентации
  блокируется с объяснением;
- **исходы**: pass / partial (сузить скоуп) / fail (вернуться в Evidence или
  убить инициативу) — каждый с автозаписью в decisions.md;
- **`/challenge` — адверсариальная репетиция**: скилл «злой стейкхолдер»
  (CFO / VP Product / скептик-инженер) атакует презентацию по реестру:
  слабые доказательства, несверенные данные, дыры в sizing. PM получает
  список пробоин до реального гейта. Это флагманская «вау»-фича релиза.

### E11. Визуализация: Opportunity Solution Tree из реестра (S)

Из `hypotheses.yaml` генерируется OST (mermaid в markdown + html в
`output/`): outcome → возможности (проблемные гипотезы со статусами/цветом
по evidence_type) → решения → эксперименты. Рынок ищет «OST + AI» (Терезa
Торрес), единственный аналог — argo (3★, только problem-space). У нас дерево
получается бесплатно из E1.

### E12. Фаза Learn: закрытие петли и knowledge base (M)

Сейчас: пайплайн кончается на GTM; «сдвинулась ли метрика через квартал» не
существует как понятие; digest помнит только названия инициатив.

Делаем:
- `/post-launch-review` (по расписанию из dependencies: «проверить через
  90 дней после launch»): факт vs target из фазы Frame; вердикты гипотезам в
  production; расхождения — в decisions.md;
- `knowledge/facts.yaml` на уровне PM (не инициативы): выученные бенчмарки
  (вида «подключённая онлайн-оплата кратно поднимает CR», «CTR сильно зависит
  от surface») с источником и датой; digest и новые инициативы подтягивают
  релевантные факты на старте;
- калибровка: «наши INFERRED подтверждаются в X% случаев» — считается из
  history реестров всех инициатив.

## Чего не делаем (анти-скоуп)

- **Не наращиваем генерацию документов** — ниша коммодитизирована (ChatPRD ≈
  хорошо промптованный Claude), смерть Zeda.io подтверждает.
- **Не добавляем шагов** — суть улучшается сжатием в фазы.
- **Не тащим данные в облако** — локальность (после 0.7.3) — правда и
  аргумент для enterprise/рынков без западных SaaS.
- **Не делаем мультиюзерность** сейчас — веб-дашборд остаётся локальным
  просмотрщиком.

## Как валидируем

Каждый эпик проверяется dogfood-прогоном на реальной (приватной) инициативе
автора: E1/E2 должны найти известные дефекты её реестра, E7 — воспроизвести
сделанный вручную ingestion внутреннего дека, E5 — поднять реально зависшие
внешние зависимости, E10 — отрепетировать реальный Gate 1.

## Порядок и зависимости

```
E1 ──► E2 ──► E3 ──► (0.8) ──► E5 ──► E6 ─┐
 │                                        ├─► (0.9) ──► E9 ──► E10 ──► (1.0)
 └────────────► E7 ───► E8 ───────────────┘             │
E4 — параллельно всему 0.8                     E11, E12 — после E9
```

Критический путь: E1 (реестр) — фундамент всего; без него E2/E3/E7/E11
строить не на чем.
